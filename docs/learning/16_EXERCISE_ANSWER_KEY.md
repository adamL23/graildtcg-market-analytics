## Learning roadmap

Raw JSON preserves the provider's exact response, supports re-parsing when code
changes, and provides audit evidence. It is inefficient for relational joins,
constraints, canonical deduplication, and Power BI relationships. PostgreSQL
provides those capabilities but stores transformed/selected fields and cannot
reconstruct an omitted or misparsed source field. Keeping both supports audit
and reliable querying.

## Chapter 3 — Environment setup

`DatabaseSettings.from_environment()` attempts `int("not-a-number")`, catches
the conversion error, and raises `ValueError: PGPORT must be an integer.` No
TCP/database connection is attempted. Restoring the original port returns the
smoke test to its prior behavior.

## Chapter 4 — Database design and SQL

1. The safe condition-price key is `(card_id, source_name, currency_code,
   printing, condition_name, listing_language)`. Source, currency, condition,
   and language are all missing from `(card_id, printing)`.
2. `NULL` passes because the check explicitly permits it; `0` passes; `-0.01`
   fails; `12.3456` passes a nonnegative check, though a narrower numeric scale
   could round or reject it. Current prices use scale 16.
3. Equal provider time plus a different hash enters the same-timestamp revision
   branch. Price, hash, provenance, and `loaded_at` are updated; the canonical
   key and provider time remain the same.
4. One valid query is:

   ```sql
   SELECT card_id, source_name, printing, currency_code,
          observation_date, count(*)
   FROM price_history
   GROUP BY card_id, source_name, printing, currency_code, observation_date
   HAVING count(*) > 1;
   ```

5. A temp table scopes and types bulk stage data but does not make multiple
   statements atomic. A transaction provides atomicity but does not provide an
   efficient set-based landing area. Together they support fast staging and
   all-or-nothing canonical loading.

## Chapter 5 — APIs and JSON

1. JSON supplies provider card ID, printing, condition, language, prices,
   sample count, and provider timestamp. Database selection supplies internal
   `card_id`; config supplies source/currency; the fetch loop supplies raw path
   and row number; normalized fields supply the record hash.
2. Ordinary parsing produces a binary `float`; Decimal-aware parsing produces
   an exact decimal token representation. The `Decimal` should be validated and
   sent to PostgreSQL `NUMERIC`.
3. HTTP 503 is a request failure; a missing key in a valid bulk map is provider
   omission/no-history; an empty sales array is a successful response with no
   returned observations in that array; malformed `data` is a validation/schema
   failure. None should be collapsed into “zero activity.”
4. Check `isinstance(value, bool)` before integer validation; parse prices as
   finite nonnegative Decimal; require timestamp timezone; require stripped
   printing text. Raise before opening the canonical database transaction.

## Chapter 6 — Python codebase walkthrough

1. `_optional_decimal` explicitly rejects booleans and raises `ValueError`.
   Fetch/normalization stops; `load_current_prices` is not called; no canonical
   row changes. The raw page was already saved by the fetch loop.
2. Provider time is source content and determines ordering/revision identity.
   `loaded_at` is generated by GraildTCG and can differ on legitimate loads; if
   hashed, identical source content could appear changed merely because it was
   ingested later.
3. Python increments `older_skipped` when incoming provider time is less than
   stored time. SQL omits the update because neither the `>` nor equal-time
   branch is true. Python provides diagnostics; SQL protects the write against
   concurrency or classification mistakes.
4. Resume scans non-success states for already saved card files, parses and
   validates the body, marks it recovered success, and updates reported credits.
   Pending IDs exclude success, so that card is not requested again.

## Chapter 7 — ETL pipelines

1. A strong failure table shows saved raw evidence, whether a same-run resume or
   offline replay is allowed, and zero/rollback canonical impact until complete
   validation. A filesystem failure must prevent a false success manifest.
2. History: card/source/printing/currency/date. Current:
   card/source/currency/printing. Condition adds condition/language. Graded adds
   raw grade. Sales: snapshot/card/printing/row number. Catalog identities are
   provider set/card identities. History is daily; current/condition/graded are
   latest/last-known state; sales is immutable snapshot position.
3. The run can be complete as an extraction because omission was distinguished
   from failure and verified. Reporting must not claim all 489 cards had
   history or interpret the omitted card as zero prices/activity.
4. The immutable snapshot is incomplete. Loading only 470 cards would present a
   partial snapshot and violate the completed-snapshot rule. Resume the same run
   until the manifest is complete, then replay offline.

## Chapter 8 — Data quality and reliability

1. Python: `older_provider_rows_skipped += 1`. SQL: zero affected rows. Stored
   hash remains the newer hash. Manifest records one older row skipped and does
   not claim an update.
2. Proven: all 481 requests succeeded; every price row had a sales array; 293
   arrays returned observations and 188 were empty. Not proven: no marketplace
   activity, complete market coverage, unique transactions, or absence of sales
   outside provider selection/window.
3. Valid: no provider-reported 30-day median/current window sales, with an older
   last sale of 80. Invalid: current value is 80; card value is zero. The fields
   describe different time semantics.
4. Matching transaction fields do not prove sameness, and different URLs do not
   prove distinct real transactions. Store provider observations and document
   identity limits; do not force cross-snapshot event deduplication.

## Chapter 9 — SQL verification and testing

1. Example:

   ```sql
   SELECT source_snapshot_key,
          count(*) AS rows,
          count(DISTINCT card_id) AS cards,
          count(*) FILTER (WHERE currency_code IS NULL) AS null_currencies,
          min(sold_date) AS first_sold_date,
          max(sold_date) AS last_sold_date
   FROM reported_sale_observations
   GROUP BY source_snapshot_key;
   ```

2. Group by card, source, currency, printing, condition, and language with
   `HAVING count(*) > 1`. A zero-row result means no duplicate groups; an
   aggregate row containing zero answers a different query shape.
3. Put the invalid insert in a `BEGIN` block and catch SQLSTATE `23514` in a
   PL/pgSQL block, then `ROLLBACK`. The final rollback also removes valid setup
   rows and prevents accidental retained changes if the expected failure path
   changes.
4. Proven: replaying the same saved snapshot does not add duplicate replay keys
   or rewrite identical hashes. Not proven: observations across different
   snapshots are the same or different real-world transactions.

## Chapter 10 — Power BI reporting

The card slicer should filter all five facts through single-direction
one-to-many relationships from `dim_cards`. A fact-to-fact relationship adds an
alternate filter path and can create ambiguity or incorrect propagation. Remove
it and keep fact tables related only through the dimension.

## Chapter 11 — Challenges and tradeoffs

Example: raw-JSON-only storage is quick initially. Costs include no enforced
canonical uniqueness or referential integrity, expensive repeated parsing for
queries, and a poor Power BI relationship surface. Scraping adds legal/contract,
anti-bot, and reliability burdens. A synthetic sale ID improves local row
addressing but falsely implies provider/global event identity unless its scope
is explicitly limited.

## Chapter 12 — Pipeline operations

1. Use `sync_reported_sales.py --resume-run SAME_RUN_ID`. Verify unchanged run
   ID, snapshot key, eligibility hash/count, scope, config budget, attempts,
   saved successes, failures, and remaining quota. Replay is permissible only
   when request manifest status is `complete`; then use `--replay-run` without
   another API fetch.
2. Baseline projected credits estimate one normal attempt per eligible card;
   reserved credits pessimistically include probes/retries before calls;
   provider-reported credits come from successful responses; the safety buffer
   is deliberately unspent quota headroom, not observed consumption.
3. Do not fetch or resume a complete raw run. Replay it offline to create the
   load manifest and canonical rows, run SQL verification, then refresh Power
   BI. Refreshing first would import stale database state.

## Chapter 13 — Mini pipeline

1. JSON `null` becomes Python `None` and SQL `NULL`. It remains distinct from
   zero. Power BI should show blank unless a measure deliberately handles it.
2. Same timestamp and changed normalized hash is
   `revised_same_timestamp=1`; the equal-time/different-hash SQL branch updates
   the row.
3. Without the hash branch, an equal-time provider correction is treated like
   an unchanged replay and cannot reach the canonical row.
4. History grain adds date, so new dates append rather than replacing the one
   latest row. A history visual must preserve date/filter context and should not
   implicitly sum observed prices.

## Chapter 15 — End-to-end worked example

1. Price, relevant market date/listing fields, provider time, hash, raw
   provenance, and `loaded_at` can change. Provider card/internal card mapping,
   source, currency, and printing remain stable for the same canonical key.
2. Same timestamp plus a different normalized SHA-256 activates the revision
   branch. Same timestamp plus the same hash is a no-op.
3. Investigate visual field duplication and aggregation first, then model
   relationships. The canonical SQL row should still be 0.13 and the source
   JSON is not expected to double itself.
